# Тест-кейс: `examples/Executor/ActiveCancel`

## Описание

Проверка двух связанных багов планировщика:

1. **Утечка `activeTasksCount` при отмене active-задачи** (баг №1).
   `Task::cancel()` не декрементировал `activeTasksCount` → после отмены
   active-задачи CPU больше никогда не уходил в сон.
2. **Транзитность `lightTasksExists`** (баг, найденный при проверке №1).
   Флаг `lightTasksExists[core]` сбрасывался каждый цикл и ставился только в
   момент срабатывания light-задачи. Если ядро долго бодрствовало из-за
   active-задач, light-задача не успевала сработать → флаг оставался `false` →
   планировщик «забывал» про ожидающую light-задачу и уходил в **deep sleep**,
   который стирает её из RAM.

## Сценарий

- `onRepeat<Light>` (1 c) — повод для light sleep.
- `onRepeat<Active>` (500 мс) — держит CPU активным (`activeTasksCount = 1`).
- `onDelay<Active>` (3 c) — отменяет active-задачу.
- `beforeEnterSleep` — индикатор сна (срабатывает только когда MCU реально спит).

## Ожидаемый результат

| Фаза | Поведение |
|------|-----------|
| 0–3 c (active жив) | ACTIVE тикает каждые 500 мс, LIGHT — каждую 1 c, **сна нет** |
| 3 c (`cancel`) | `### SLEEP (Light)` — сон срабатывает (`activeTasksCount` обнулился) |
| После cancel | режим **light** (не deep), пробуждение по таймеру ~1 c, LIGHT продолжает стрелять, ACTIVE останавливается |

Без фикса №1 строка `### SLEEP` не появилась бы никогда (счётчик утёк).
Без фикса `lightTasksExists` после cancel был бы **deep sleep** (light-задача теряется).

## Запуск

```bash
pio run -e executor_active_cancel -t upload
pio device monitor -p COM10
```

## Фактический результат (зафиксировано на COM10)

```
ACTIVE tick @ 536/1036/1536/2036/2536/3036 ms   ← active-spin, сна нет
LIGHT  tick @ 1002/2002/3002 ms
>>> cancel ACTIVE @ 3036 ms
esp_light_sleep_start ... sleep time: 964239    ← LIGHT sleep (исправлено)
### SLEEP (Light) @ 3040 ms
LIGHT tick @ 4001 ms                            ← пробуждение по таймеру, light-задача работает
```

**Статус: PASS.**
- `### SLEEP` срабатывает только после `cancel` → фикс №1 работает (`activeTasksCount` корректно декрементирован в `cancel()`).
- Режим сна — **Light** (а не Deep) → фикс `lightTasksExists` работает: ожидающая light-задача удерживает light sleep даже после окна active-spin.

## Примечания / известные ограничения

1. **Гонка ядер устранена рефакторингом.** Per-core состояние (`lightTasksExists`,
   `tickTasksExists`, `minSleepTime`) теперь считается в локальных переменных и
   **публикуется одним записыванием** после per-task цикла, пока
   `coreSleepReady[core] == false`. Ядро, захватившее мьютекс, читает
   согласованный снимок — это убрало периодические уходы в deep sleep
   (наблюдавшиеся до рефакторинга: ~1 deep на несколько light).

2. **Один «лишний» ACTIVE tick ~1 с после `cancel`** (напр. `@ 3997 ms`).
   Вероятная причина — финальный колбэк `esp_timer` при удалении периодического
   таймера. На `activeTasksCount` не влияет (счётчик уже обнулён в `cancel()`),
   поэтому сон не блокируется. Требует отдельного разбора (см. список багов).

3. **Мониторинг USB-serial (CH340) во время light sleep нестабилен**: в устойчи-
   вом light sleep устройство не перезагружается, поэтому между пробуждениями
   вывод почти не виден. Это особенность USB-UART во время light sleep, а не баг
   логики. Для уверенности в детерминированности пользуйтесь индикатором
   `### SLEEP (Light)` и логом `esp_light_sleep_start` (они печатаются в окне
   бодрствования).

## Связанные баги

- №1 — утечка `activeTasksCount` при `cancel()` (исправлено).
- `lightTasksExists` транзитность + гонка ядер (исправлено).
- (наблюдение) финальный колбэк `esp_timer` при удалении periodic-таймера —
  открытый пункт.
